## 9 轮 live canary 对照

同一段 9 条消息，两个新 WebChat 会话：

| | shadow | live（replace） |
|---|---:|---:|
| 非缓存输入 | 64,709 | 97,532 |
| 缓存输入 | 115,200 | 81,792 |
| 总输入 | 179,909 | 179,324 |
| 输出 | 1,039 | 981 |
| 估算价格 | ¥0.1953 | ¥0.2438 |

结论：

- 总输入 token 只降了 **0.3%**，价格反而 **高了 24.8%**。
- 原因不是插件“没生效”：live 的 `injected_tokens` 约 5.6k，模式为 `full/l1`，确实接管了上下文。
- 原因是这个环境的其他插件/人格/system prompt 每轮仍注入约 18k token；同时 live 的缓存命中结构变差。
- 9 轮太短，历史本身还没成为主要成本；这个对照**不能**证明长期节省，也不能证明长期更贵。

## 50 轮 shadow vs live 最终对照

两个全新 WebChat 会话，同一模型、同一组 50 条消息，其他注入型插件关闭；shortcircuit 关闭，只比较上下文本身。

| | shadow 基线 | live（replace） |
|---|---:|---:|

| 缓存输入 | 739,968 | 497,280 |

| 前缀末 20 轮稳定率 | 95% | 95% |
| 长期线索最大字符 | 41 | 41 |

结论：

- 总输入下降 **24.1%**（844,561 → 640,717）
- 实际按价估算下降 **8.2%**（¥0.62636 → ¥0.57529）
- 输出下降 **15.7%**
- 非缓存输入反而增加 **37%**，缓存输入下降 **33%**：live 的稳定前缀/窗口改变导致部分缓存命中丢失，所以“输入 token 降 24%”没有等比例变成“价格降 24%”
- 50 轮还没有让基线接近上下文耗尽，因此这不能验证“寿命延长到多少”，只能证明 50 轮内的实际成本和上下文规模
- 这次结果也没有复现 98%；98% 仍只是特定 128k/全量历史/无缓存假设下的长期模型估算

## 32k 实际耗尽测试

把当前 provider 临时降到 `max_context_tokens=32768` 后，用两个全新 WebChat 会话跑同一组 100 条消息（50 条脚本重复两次）：

- 基线在第 **91 → 92 轮**发生截断：上一轮总输入 26,993，下一轮掉到 15,398
- 也就是 **第 91 轮后撞到 32k 窗口**

| 截至第 91 轮（撞窗前） | shadow 基线 | live |
|---|---:|---:|
| 非缓存输入 | 183,468 | 252,892 |
| 缓存输入 | 1,596,800 | 914,304 |
| 总输入 | **1,780,268** | **1,167,196** |
| 输出 | 10,137 | 7,557 |

| 唤醒率 | 14.3% | 14.3% |
| 末 20 轮前缀稳定率 | 90% | 90% |

- 总输入下降 **34.4%**
- 实际价格下降 **17.9%**
- 两组到撞窗点的总成本约 **¥2.27**
- 若继续跑到 100 轮（基线已截断后）：shadow ¥1.36701、live ¥1.12870，价格仍约 -17.4%
- 32k 下前缀稳定率从 95% 掉到 90%，是因为窗口截断本身改变了前缀；这不是插件理想状态下的数字

测试结束后已把 `max_context_tokens` 恢复为 **200000**，配置恢复为 shadow、空白名单、host off。

## 到 200k 上下文耗尽的外推

当前 provider 的 `max_context_tokens` 是 **200,000**。按 50 轮真实曲线做线性回归（预留 4k 输出）：

| | shadow 基线 | live |
|---|---:|---:|
| 每轮总输入增长 | 约 +166 token/轮 | 基本恒定 |
| 到 195k 预计轮数 | 约 **1,103 轮** | 不因历史增长耗尽 |
| 每轮成本（约） | 从 ¥0.013 涨到 ¥0.10 | 约 ¥0.0115 |
| 到 1,103 轮总成本 | 约 **¥64** | 约 **¥13** |
| 50 轮/天所需时间 | 约 22 天 | 可继续 |

- 只跑基线到耗尽：约 **¥64**。
- 做一组 A/B 到同一轮数：约 **¥64 + ¥13 = ¥77**。
- 这里的价格按当前配置：输入 ¥2/M、缓存 ¥0.5/M、输出 ¥8/M；实际账单会受缓存命中、重试、工具调用影响。
- 这是从 50 轮外推，不是实际跑到 1,103 轮；真实曲线可能因 AstrBot 截断、缓存策略、回复长度变化而偏离。

## 缓存边界回查（100 轮 32k 会话）

事后逐轮回查 `0a51ddd0…` 这个 100 轮 32k 会话的 `metrics` 表，缓存命中结构非常整齐：

| 轮次类型 | 缓存输入 | 非缓存输入 | 出现次数 |
|---|---:|---:|---:|
| L0 线索块未变 | 10,752 | 约 1,900–2,300 | 92 |
| L0 线索块变化 | **2,816** | 约 9,600–10,100 | 8 |

- 8 次变化里有 **7 次**造成真正的缓存断档（另一轮是连续变化，断档已在上轮付过），每次多付 **7,936** 非缓存 token；
  合计 **55,552**，占该会话非缓存输入（279,356）的 **19.9%**，按价约 ¥0.11 / ¥1.13。
- 2,816 与 10,752 都是 128 的整数倍，符合“前缀在 L0 处断开、后面按块重算”的特征。
- 线索块本身只有 30–41 字。真正被作废的是它**后面**的内容：AstrBot 在插件 hook 之后会把技能/工具说明追加到
  `system_prompt` 末尾（读 `astr_main_agent.py` 可见 `req.system_prompt += tool_prompt`），实机约 7.9k token。
- 同一批数据里，窗口每轮都在滑动（`recent_chars` 忽大忽小、历史起点每轮变），所以历史部分几乎从不命中缓存：
  稳定状态是“系统提示命中、最近窗口全价”。

结论：32k 实测的 `-17.9%` 价格降幅是在这个布局下拿到的。把线索移到请求末尾、窗口改成粗粒度回收，
理论上还能再拿回这部分损失。

| | shadow 基线 | live 0.1.1 | 变化 |

关键：**线索块变化 4 次，一次都没有造成缓存回落**。live 侧 8 次缓存回落全部是窗口回收
（`recent_chars` 从约 600 字掉到约 300 字），单次 256–384 token，合计 2,944 token。

模拟预测（`cache_prefix_sim.py`，60 轮 + 7.9k 宿主后缀）是 -11.1%；实机 -28.8% 更高，
因为本地宿主的系统提示更小、基线历史增长更快，live 的窗口收益更明显。

仍未解决：
- **输出短了 21.8%**。这次 live 的平均回复 31.6 字 vs 基线 40.4 字，和之前“live 输出少约 25%”一致。
  是更简洁还是变敷衍，仍然没有盲测结论（P2）。
- **`replace` 会改写宿主的会话记录**：live 会话在 AstrBot 自己的 `data_v4.db` 里只剩 11 轮
  （152 条 → 23 条），shadow 会话保留全部 50 轮；插件自己的 `turns` 表仍有 50 轮。
  与宿主自带记忆/历史共存时应选 `off` 或 `prepend`。

## 1M 窗口外推（模型预测，不是实测）

用上面 50 轮 A/B 的真实 `usage` 拟合每轮上下文增长（`scripts/projection_1m.py`）：

```text
基线：context(n) = 8,226 + 209 n    每轮新输入 2,090   输出 159
插件：context(n) = 8,649 +   2 n    每轮新输入 2,065   输出  64
价格：输入 ¥2 / 缓存 ¥0.5 / 输出 ¥8（每百万 token）
```

校准：32k 下模型预测第 97 轮撞窗、累计 ¥1.32；实机 32k 测试是第 91 轮、¥1.25。偏差 6% 以内。

| 窗口 | 基线撞窗前轮数 | 约合天数（50 轮/天） | 基线下线 | 插件同轮数 | 插件跑 3 倍轮数 |
|---:|---:|---:|---:|---:|---:|
| 32k | 97 | 2 | ¥1.32 | ¥0.77（-41%） | ¥2.35 |
| 128k | 553 | 11 | ¥20.70 | ¥4.55（-78%） | ¥14.57（-30%） |
| 200k | 898 | 18 | ¥49.79 | ¥7.54（-85%） | ¥25.07（-50%） |
| 1M | 4,729 | 95 | ¥1,207.97 | ¥48.89（-96%） | ¥214.78（-82%） |

每 1,000 轮：基线到第 1,000 轮时单轮上下文 21.7 万 token，累计 ¥112.92；插件 ¥8.95。

必须带上的前提：

- 模型只算“历史随轮数增长”。宿主的工具/技能注入是**常数项**，不随轮数变；1M 下它被摊薄，短会话里它反而是主导项。
- AstrBot 撞到 `max_context_tokens` 不是硬停：会截断，或由 compact/idle_compact 这类插件压缩。所以“寿命”应理解为
  **上下文开始失真之前的轮数**，不是服务停摆；压缩之后账单继续涨，记忆已经打折。
- 价格用插件配置里的单价；provider 实际计费、缓存 TTL、重试、工具调用都会改变曲线。

## 质量盲测第一轮（49 对，人工 + 机器各判一次）

数据：本地 A/B 的 49 对同题回复（`validation_50.jsonl` 的第 2–50 轮；第 1 轮因两个会话各带
不同的 10/22 旧消息而作废）。同一批回复做了两次盲判，来源都隐藏、顺序随机：

1. **人工**：`reports/quality_sheet_local.html`，点 1–5 打分 + 二选一。
2. **机器**：`scripts/quality_judge.py`，Qwen3-VL-30B，每对正反各判一次。

### 人工结果（有决定权的那份）

| | 基线 | 真心 |
|---|---:|---:|
| 平均分（1–5） | 3.90 | **4.16** |
| 二选一胜场 | 10 | **21** |
| 平局 | 18 | 18 |

决定性 31 对里真心赢 **68%**。平均回复长度 31.4 字 vs 40.4 字：**更短，但人更喜欢**，
所以“输出变短 = 变敷衍”这个担心在这批数据上不成立。

### 机器判不可靠

同一批数据，机器判是 21:22（平局），与人工逐对一致率只有 **29%**——50 对里 35 对结论不同。
结论：这类“有没有人味 / 接得自不自然”的判断，小模型 judge 只能当噪声，不能当证据。

### 真心输掉的 10 对，分成三类

| 问题 | 例子 | 根因（已定位到代码/数据） |
|---|---|---|
| 不知道却编造 | `上次说的阿哲，是不是搞摄影的` → 答“算半个吧，他平时爱到处拍” | L0 里根本没有“阿哲”这条线索，模型没有“我不知道”的出口 |
| 太短、被截断 | `嗯`、`晚安` 的回复比基线短一半 | `aux.rhythm.postprocess` 按 `max_chars`（本次 50 字）硬裁 |
| 关键事实没被注入 | `我不吃香菜` 答成“香菜党表示抗议啦” | 槽位里有“不吃香菜”，但注入的是“养了猫/生气/看医生”三条，关键偏好掉出 k=3 |

另外 L2 把问句抽成了事实：`不吃什么吗` 被写成一条 habit 线索，属于噪声。

## 对“98%”的影响

这次实机数据说明：**在插件很多、system prompt 很大、缓存命中结构复杂的真实 AstrBot 里，真心不一定立刻省钱，甚至短期可能更贵。**

要验证真实节省，必须：

1. 暂时关闭 LivingMemory 等会注入上下文的插件；
2. 用同一个模型、同一段 50 轮对话；
3. 对比 `actual_total_input_tokens` 和 `actual_cost`，而不是插件自己的 `injected_tokens`；
4. 至少跑到历史明显增长（>30 轮）再看曲线。

在此之前，不能把 98% 作为对外承诺。
